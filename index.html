How you build it

Interoperability first, then agents you can trust

An agent is only as safe as the data and the access it is given. Build a clean, standards-based data layer first, then put agents on top of it that work through the same governed APIs and controls as every other consumer.

01 · Connect

Connect any healthcare system

Prebuilt connectors reach the systems where care data lives, whether they speak FHIR, HL7, DICOM or a proprietary API.

  • Prebuilt EMR connectors for Epic, Oracle Health (Cerner) and athenahealth, and generate a connector for any other EMR
  • FHIR server connectors for any FHIR R4 repository or EHR API
  • HL7 v2 over MLLP/TCP and file servers, and DICOM for imaging systems
  • Databases, claims platforms and any REST endpoint

Open source

Open-source building blocks, ready to run

Apache 2.0 licensed components you can run today and own outright: a FHIR Server, a FHIR MCP Server, a FHIR Terminology Server and a catalog of prebuilt services.

FHIR repository

FHIR Server

A fast, lightweight FHIR R4 server written in Go and backed by PostgreSQL.

  • Fastest open-source FHIR server in a third-party benchmark
  • Full REST API, search, validation and IGs
  • Under 25 MB, starts in under a second
Docs GitHub

AI access

FHIR MCP Server

Exposes any FHIR server or API as MCP tools for AI assistants and agents.

  • search, read, create, update and delete tools
  • SMART on FHIR authorization
  • Works with Claude Desktop, VS Code and agents
Docs GitHub

Terminology

FHIR Terminology Service

A FHIR R4 terminology service for CodeSystems, ValueSets and ConceptMaps.

  • $expand, $validate-code, $lookup, $subsumes and $translate
  • Loads SNOMED CT, LOINC, ICD-10-CM and FHIR code systems
  • Plugs into the FHIR Server

Reference implementation

Client registry (MPI)

A standards-based master patient index that keeps one trusted identity for each patient across the exchange.

  • IHE PDQm and PIXm: demographics query (ITI-78), identity feed (ITI-104) and match (ITI-119)
  • Blocking-based matching and incremental deduplication, with match rejection
  • A management UI, FHIR AuditEvent logging (IHE ATNA) and any OIDC identity provider
Client registry

Reference implementation

Interoperability layer

The central message router of the exchange. It receives FHIR and HL7 v2 messages, routes them to the right services and publishes audit events.

  • HTTP and MLLP/TCP listeners for FHIR and HL7 v2 clients
  • HL7 v2 ↔ FHIR transformation with the Ballerina health libraries
  • WebSub event hub, audit service and OpenSearch dashboards
